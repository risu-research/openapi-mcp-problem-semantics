# RISU Probe — P0–P4 gate review and independently measurable next experiment

## Stay on the original plan

The five-gate roadmap remains the right order. Product work happens only on
experiment branches; the research main and proven prior versions remain frozen.

| Gate | Current verified scope | What it cannot yet claim |
|---|---|---|
| P0 Decision consistency | v0.9.4 CLI, JSON, Markdown, SARIF and exit-policy consistency tested on Windows/Linux | No guarantee for unknown future renderers |
| P1 Consumer Witness | v0.9.4 real MCP outputs tested by two deterministic consumers; a real SDK contract can make the difference concrete | Does not predict real LLM behavior |
| P2 Minimal Reproducer | v0.9.5 recursive-deletion 1-minimal payloads independently replayed against real generated MCPGen | Not globally shortest; not every external spec supported |
| P3 Fix Verification | v0.9.5 two incident repairs on authentic SDK dispatchers; v0.9.6 adds actual live positive controls and idempotent typed preservation | Does not prove one patch safe for all converters, SDKs, or untrusted servers |
| P4 Independent adoption | Design and evaluation protocol below | No independent unaffiliated developer has yet completed the challenge |

## Why P3 needed another round

A patch that repairs two selected examples can still regress existing valid
structuredContent, successful HTTP 200 responses, or unrelated errors. P3
therefore requires: incident before/after, positive and negative real-SDK
controls, preserving already typed data exactly, rejecting status conflicts,
and a mutation that would detect a broken repair. Synthetic localhost is an
appropriate safe validation environment, but not a production compatibility
claim.

v0.9.6 checks six extra live generated-tool controls: PyGithub 404 generic
error, PyGithub 401 authentication, Stripe 400 invalid request, Stripe 401
authentication, and two valid HTTP 200 bodies. Each is compared against
unaltered pinned SDK logic (or original success body), and every control
checks original structuredContent passthrough separately. The two initial
failures remain independently replayable with 1-minimal input.

The app code and direct artifact are on this branch; do not use unverified
local results to claim success. CI record and evidence ZIP must pass before
promotion. Runtime is intentionally offline, read-only, nonroot, and uses
only GET over 127.0.0.1.

## Reproduce P3 without knowing the source API

A developer with a clean checkout and Docker can run one explicit command:

    bash apps/verify_fix.sh --allow-build-downloads --output /tmp/risu-p3-evidence

This command (1) uses git archive to copy only tracked approved source dirs,
(2) restores SHA-pinned product code, (3) downloads pinned public SDK
dependencies during the container BUILD after explicit opt-in, (4) disables
network and all privileges during each TEST RUN, (5) generates synthetic MCP
and source fixtures, (6) proves the old bridge failures and fixed bridge
recoveries on unchanged SDK code, (7) proves six controls, (8) independently
audits all results, and (9) exports an evidence bundle. It refuses to
overwrite an existing output directory. It never runs against provider APIs.

The build stage itself is not offline. Docker and enough machine resources
are prerequisites. Dependencies beyond exact upstream commits are not fully
hash locked; this is a reproducible snapshot under a controlled CI runner,
not a cryptographically complete build closure.

A downloaded ZIP's fixtures can be inspected offline; if the user wants
the actual original SDK classification check, the same exact SDKs must be
available. No user credentials or non-synthetic payloads should be supplied.

## P4 independent-use preregistration

P4 cannot be passed by our own CI, the author rerunning the same fixture, or
three synthetic endpoints generated by the same harness. We need people
unaffiliated with our test design using real independent application specs.

**Minimum pilot:** three unaffiliated developers, each with a distinct
public real-world OpenAPI application project, no special fixture supplied
and no developer taught RISU's expected failure. Recruiting and consent must
occur before observations. GitHub issues or PRs should never be posted
without project maintainer consent.

**Beginning:** clean clone/time recording, operating system, API description
size, tool generator and version, whether runtime calls are allowed, and any
limits. Stopwatch starts before installation; measure *first meaningful
diagnosis* separately from full runtime confirmation and from successful
repair. No hidden exclusion of installation errors or unsupported projects.

**Safety:** first run offline static check; then, only with authorization,
run allowlisted GETs against a local disposable API. Record denied actions
rather than silently skipping them. Do not collect tokens, user business
payloads, private API responses, environment secrets, or raw connection logs.

**Primary prespecified metrics:**
- First meaningful and defensible finding or justified no-finding within
  10 minutes from the clean setup. Count unsupported and timeout cases.
- Fraction of the three developers able to independently replay a finding
  without original production API access.
- Confirmed false-positive/false-negative rate on hand-reviewed positive and
  negative *relevant* controls, including explicit uncertainty outcomes.
- Which observed failures become concrete minimized reproductions with
  source hash and usable repair/CI regression evidence.
- Developer actions, manual edits, and minutes required, including aborted
  attempts.

**Reasonable first pilot bar:** at least 2 of 3 complete an interpretable
first check within 10 minutes; at least 2 have independently replayed
approved cases; at least one independently discovered issue has an
author-verified source/consumer mismatch (or report that zero were
discovered). No misleading inference from a tiny sample; classify only as
a pilot. Do not call P4 complete without these field observations.

**Advance to a wider beta only after:** accepted developer feedback,
documented safety and unsupported cases, comparable projects and clear
reproduction instructions. Avoid introducing dashboards, speculative LLM
claims or expanding to unrelated security scanners before these criteria.
