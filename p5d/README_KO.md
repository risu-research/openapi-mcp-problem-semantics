# RISU Probe P5-D: Windows installation, first diagnosis latency, error clarity, and multirepository success

**Design:** P5-C production wheels are rehydrated from immutable CI-verified `0.9.18.dev0` baseline (SHA-256 in `prepare_base.py`), P5-D adds only a command router and a diagnostic presentation layer. Twelve existing static/causal/schema modules remain byte-identical. The new artifact is `risu-probe-preview==0.9.19.dev0`, a development build, not a PyPI release.

**Commands:** `risu-probe check .`, `risu-probe check . --format json`, `risu-probe check . --timing`, `risu-probe doctor` and `risu-probe doctor --format json`. Existing `risu-probe.json` configured-project `check` and prior CLI commands are forwarded unchanged. Do not interpret `NO_STATIC_FINDINGS` as a conformance guarantee. The default check never executes target modules or remote APIs. Static hypotheses remain hypotheses; saved-replay evidence requires separate CI provenance verification.

**Error experience:** `RCHK101` missing/symlink project path, `RCHK102` symlink evidence, `RCHK103` file/byte budget, `RCHK104` rejected saved replay, `RCHK105` refusal to overwrite, `RCHK106` permissions, `RCHK199` other incomplete scans. Each CLI error has a concrete next action. Incomplete YAML OpenAPI (optional PyYAML absent), unsupported file types, and static incompleteness remain visible as `UNVERIFIED` instead of being counted as completed coverage.

**Cross-platform qualification:** the same build protocol and actual installed wheel are tested with `windows-latest` and `ubuntu-latest`, both Python 3.11. The installed Windows `risu-probe.exe` is executed, not just a Linux cross-compiled wheel. Each OS checks Unicode + whitespace paths, safe first diagnosis, offline default, CLI command retention, target source not executed, and new source tests.

**Benchmark:** `external_repos.json` pins 10 public Git commits across Python libraries, vendor SDKs, two MCP frameworks, official MCP servers, OpenAPI-to-MCP generator, and API framework. The runner checks out only exact commits; does not install external dependencies, run project code, invoke submodules, or start servers. For each repository, baseline 0.9.18 and new 0.9.19 run in separate fresh processes 3 times each. `first_ms` is first process launch + scan + serialization. `median_ms` is median of 3 launch/scan processes, not warm in-process performance. Each project separately records `commands_completed` and `complete_source_scans`. A tool process exiting 0 with unverified files is not counted as a complete source scan. Clone/download time is excluded. Filesystem cache and CI load are uncontrolled; no cross-platform speed ranking or population-wide success-rate claim.

**Reproduce:** fetch pinned public repos and installed build wheels using the repo CI workflow, or run `python p5d/ci_driver.py --base-wheel path/to/verified-0.9.18.whl --repeat 3` with Git and Python 3.11, setuptools/wheel installed. Individual scan via `risu-probe check .`.

**Evidence:** `p5d/results/windows.json`, `p5d/results/linux.json`, exact wheel SHA-256 identity, GitHub workflow jobs, explicit error examples and new regression tests. A CI status is not evidence of user adoption, production outages, or total MCP compatibility.
