# Reviewer Attack Surface

The project is strongest when it anticipates the hardest fair objections rather than accumulating more targets.

## 1. “You only tested three translators.”

**Valid limitation.** Do not claim prevalence. The contribution is replicated existence plus mechanism diversity, not a market survey.

Best response: three tested architectures independently fail the same bounded invariant; the paper scopes every product claim to a version or commit.

## 2. “CNOE is not independent because it uses FastMCP.”

**Partly correct.** Never call all three completely independent MCP implementations.

Best response: CNOE is a distinct translation architecture whose source Problem object is dropped in generated tool code before the FastMCP runtime boundary. Its evidentiary value is the separately localized loss mechanism.

## 3. “MCP simply cannot represent RFC 9457.”

**Directly tested alternative hypothesis.** E7 is the answer. The same frozen corpus is preserved across an actual official MCP 2026-07-28 TypeScript v2 stdio boundary.

Do not overstate: this proves sufficient carrier capacity only for the semantics exercised by v0.1.

## 4. “Your oracle only likes structuredContent.”

**Addressed before E5–E7.** Adapter v0.2 recognizes representation-neutral machine carriers including explicitly typed embedded `application/problem+json` resources. E7 uses that path. Ordinary text remains non-machine-addressable.

## 5. “You designed the positive control to pass your own oracle.”

**True but not fatal; clarify its role.** E7 is not an unbiased product evaluation. It is a constructive existence proof. The important constraint is that the oracle/corpus were frozen before the wire run and the negative text-demotion control still fails.

## 6. “Your 12 cases do not cover RFC 9457.”

**Correct.** Never claim completeness. The corpus is boundary-oriented: identity, defaults, occurrence, extensions, localization, media-type gating, prose non-inference, and status provenance.

## 7. “Why preserve observed HTTP status at all?”

Because the translation begins from an HTTP response envelope, not the JSON body alone, and P11 deliberately demonstrates that observed status and body `status` can represent distinct facts. This is a profile design choice for translation fidelity, not a claim that RFC 9457 mandates an MCP status field.

## 8. “`retryable=true` in E6 proves invention.”

Do not make that claim in the primary result. The observed field is non-standard top-level `meta`, not protocol `_meta`, and retry policy can depend on method/context. Preserve it as an adjacent observation unless a future profile defines and justifies the semantic entailment boundary.

## 9. “These are implementation bugs, not a standardization issue.”

Possible, and the paper need not deny it. The profile's value is precisely to make such implementation-level fidelity bugs executable and reviewable. Whether the remedy becomes library patches, best-practice guidance, or a formal profile is a subsequent governance question.

## 10. “Why not test ten more converters?”

Because the marginal information value is currently lower than publication hygiene and external review. A fourth loss result changes 3→4; an independent reproduction, public frozen artifact, or external implementation passing/failing the profile changes credibility more substantially.
